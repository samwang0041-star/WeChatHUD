# 日报方案评估标准

## 评分维度

### 1. 数据完整性 (Weight: 30%)
日报方案是否解决了「数据枯竭」这个根本问题？

**具体信号：**
- 是否有独立的数据采集层，不依赖 retrospective run？
- 数据采集是否覆盖聊天记录、asks、commitments、reply debt 等多源数据？
- 是否有明确的消息筛选/去噪策略？
- 是否有 Token 预算控制和硬上限机制？

**评分示例：**
- 优秀 (9-10): 有完整的轻量级扫描器，能从聊天记录自动提取丰富上下文，有明确的上限和去噪策略
- 合格 (6-8): 有新的数据源接入，但扫描范围或筛选策略不够明确
- 不及格 (0-5): 仍主要依赖 retrospective 数据，或没有解决数据空洞问题

### 2. AI 生成质量 (Weight: 25%)
AI 生成的日报是否高质量、低幻觉、可直接使用？

**具体信号：**
- Prompt 是否充分利用原始数据（而非仅聚合指标）？
- 是否有防止幻觉的机制（如要求引用具体来源、heuristics 校验）？
- 是否有 retry/fallback 策略应对 AI 失败？
- wechatDraft 是否符合「三段式」标准格式？

**评分示例：**
- 优秀 (9-10): Prompt 设计精良，有多层防幻觉机制，fallback 策略完善
- 合格 (6-8): Prompt 有改进，但防幻觉或 fallback 策略有缺口
- 不及格 (0-5): 仍是模板替换风格，AI 输出质量无保障

### 3. 技术可落地性 (Weight: 25%)
方案是否能在现有代码库中实现，改造量合理？

**具体信号：**
- 数据模型是否与现有模型兼容？
- 服务拆分是否遵循现有架构模式（actor + protocol）？
- 是否有明确的改造范围和侵入点？
- 是否考虑了向后兼容？

**评分示例：**
- 优秀 (9-10): 改造量小，与现有架构无缝集成，向后兼容
- 合格 (6-8): 改造量中等，有兼容方案但需一定迁移工作
- 不及格 (0-5): 需要大规模重构或推翻现有架构

### 4. 用户体验 (Weight: 20%)
用户从打开到获得可用日报的全流程是否顺畅？

**具体信号：**
- 是否有自动预热/缓存机制，打开即看？
- 失败时是否有清晰的错误信息和重试入口？
- 是否有数据来源标识，让用户信任日报内容？
- 是否提供一键复制等便捷操作？

**评分示例：**
- 优秀 (9-10): 打开即有内容，流程顺畅，失败处理完善
- 合格 (6-8): 基本可用，但缺少某些体验细节
- 不及格 (0-5): 仍需手动操作，失败时无反馈

## 惩罚项
- 依赖外部 API（日历、企业微信等）- 扣分
- 引入新的复杂依赖（新的数据库、新的 AI provider SDK）- 扣分
- 方案过于宏大，无法在 2 周内落地 - 扣分
- 没有明确的 Token/性能预算 - 扣分
- 忽略现有代码约束（如 actor 隔离、@MainActor）- 扣分

## 通过标准
总分 ≥ 7.5/10，且「数据完整性」和「技术可落地性」均 ≥ 7/10。
