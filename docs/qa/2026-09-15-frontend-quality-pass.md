# 前端质感改造验收（2026-09-15）

目标：全面优化动画质感、交互文案、前端，参考 CleanMyMac 5 的 UI 效果。
本文记录**这一次实测到的证据**，不是计划。参考对象是本机 `/Applications/CleanMyMac_5.app`，
通过真实点击其侧栏（智能呵护 → 垃圾清理）截图取样，不是凭记忆描述。

## 参考对象实测（CleanMyMac 5）

打开本机 CleanMyMac 5，读其 AX 树并截图，得到四个可复用的结构性事实：

1. **侧栏每一行是一个彩色圆角图标块 + 文字**（`IntroViewCategoryItem-*`）。模块色是该产品最强的识别符。
2. **页面主区有一层跟随模块色的环境光**：智能呵护是紫、垃圾清理是绿，整页底色随模块变。
3. **大标题 + 一行副标题 + 三个要点**，正文极少；页面的工作就是让你看懂"这是干什么的"。
4. **底部只有一个发光的胶囊主按钮**（`UbiquitousContentButton`），页面其余部分全是中性面。

据此推导的设计语言见 `docs/design/ui-language.md` 的「材质与光（v2）」。

## 改了什么

### 1. 一套材质与光源（`CompanionMaterial.swift`，新增）

- **一个光源，从上方照**：所有抬起的面都同时有①顶边发丝高光②面部自上而下的浅渐变③一层柔和阴影。
  原先是"一个填充色 + 1pt 边框"的平涂，一页八张等重卡片没有深度线索。
- **环境光**（`CompanionBackdrop`）：详情页底色 = canvas + 从顶部散开的模块色径向光晕。
- **模块色**（`SettingsView.Tab.accentColor`）：18 个模块各自的强调色，贯穿侧栏方块、页头方块、环境光、选中行填充、筛选胶囊。
- **发光主按钮**（`CompanionGlowButtonStyle`）：页面上唯一"看起来是下一步"的东西，对应参考产品的扫描按钮。
- **呼吸状态灯**（`CompanionStatusDot`）：替代状态栏里重复文字的图标；同步中会呼吸，reduceMotion 下改静态环。

`CompanionSurface`（既有的卡片修饰器）改为走新面板，因此**全站既有卡片一次性获得新材质**，不是逐页重写。

### 2. 动效成组（`CompanionMotion`）

- **错峰入场**（`companionStagger(index:)`）：切页时内容按阅读顺序依次到位，位移 6pt、步进 45ms、整组约 240ms、**封顶第 6 个**。
- 新增 `cardHover` / `sidebarSelection` / `pulse` 三条曲线，全部过 `CompanionMotion` 闸门（reduceMotion 下返回 nil）。

### 3. 交互文案分层（`CompanionInteractionCopy.swift`，新增）

`CompanionProductCopy` 管"东西叫什么"；新文件管"用户正在操作时界面对他说什么"，三条硬规则：
说结果不说实现、每个等待都要有承诺、每个失败都要有下一步。

落到真实控件：

- 侧栏 18 行每行有了**说明这页干什么用**的 tooltip/VoiceOver hint，且与标签不同（有测试断言）。
- 状态栏等待态说明在读什么、读多少（`readingChats(n)`），不再是一句无法度量的"正在读取"。
- 简报卡加载态改为"正在理出大家在聊什么、为什么找你"，说明在等什么。
- 失败态统一带下一步；简报卡三个小卡换上发光字形槽，形成可跟随的阅读序列。
- 空态副本、撤销副本、完成度副本（`handledToday`）成文。

### 4. 修掉的真实缺陷

| 缺陷 | 事实 |
|---|---|
| 提示条边框恒为橙色 | `HUDRootView` 的 toast 无论成功失败都用 `Color.orange` 描边：绿色对勾的"已撤销"戴着警告框。改为跟随语义色。 |
| 侧栏页脚压住滚动内容 | `safeAreaInset` 没有自己的底色，滚动行透到"本机数据"下面；页脚改为不透明底，页头改为渐隐底。 |
| `待办`筛选是手写副本 | 与 `CompanionFilterPill` 同尺寸但锁死品牌绿、且没有选中态抬起，同一控件在站内有两种长相。已统一并接入模块色。 |
| 筛选胶囊全站品牌绿 | 与页面的模块色无关，选中态读起来像主操作。改为各页自己的模块色 + 轻度辉光。 |
| 卡片顶边高光有接缝 | 高光原先用 `trim(from:0,to:0.5)` 描半个路径，首尾相接处可见断点。改为整圈渐变描边。 |
| 引导页/使用指南用原生系统字体 | 与全站 token 不一致，一页像另一个 app。已归入 `workspaceTitle/workspaceBody` 与卡片材质。 |

| **分组标题与它唯一的行重复同一句** | 自动回复「连发时等几秒一起回」、使用偏好「显示位置」、AI 服务「服务来源」都是 `SettingsSection(X)` 里放 `SettingsRow(X)`，同一句话上下连排两遍，读起来像渲染错误。改为标题说分组、行说控件；并补 `testSettingsSectionsDoNotRepeatTheirOnlyRowsTitle` 永久拦住该模式（该正则当前匹配 8 处配对）。 |

### 5. 顺带修掉的 QA 阻断（非 UI）

预览构建读正式包的钥匙串项（`com.wechathud.secrets`），会在每次预览启动时弹系统密码框，
**把后面所有界面都挡在解锁对话框之后**，导致自动化走查无法进行。
`HUDStore` 在 `PreviewRuntime.isEnabled` 时改用进程内密钥存储：预览本来就不连真实服务商。

## 实测证据

### 构建与测试

- `swift test`：**1559 个用例通过，0 失败**，11 个显式跳过（无本地微信库 / 无 live AI 端点）。
- `swift build -c release`：**零警告零错误**。
- 新增 `CompanionMaterialTests`（18 个用例）锁住设计系统本身：光源方向（顶边必须亮于底边）、
  悬停位移上限、环境光上限、错峰延迟封顶、reduceMotion 下全部归零、18 个模块色互异、
  每页 hint 与标签不同、失败文案必带下一步、空态不是死路、计数在 0 与 N 时都成句。
- 既有的 `ChromeMotionHygieneTests` 仍全绿：全站没有裸 `withAnimation(`，动画一律过闸门。

### 动画实测（真跑，非推断）

`--preview-peek` 自驱动 compact → peek → extended，由进程内记录窗口帧时序，`$TMPDIR/wechathud-peek-qa.json`：

| 阶段 | 宽 × 高 | 时长 | 实测 FPS | 最差帧 |
|---|---|---|---|---|
| compact | 297 × 32 | 起始 | — | — |
| peek | 449.6 × 31.5 | 飞行中 | 60.0 | 17.06 ms |
| peek 落定 | 453 × 32 | 392 ms | 60.0 | 17.06 ms |
| extended | 560 × 252 | 400 ms | 60.0 | 17.01 ms |

结论：形态弹簧全程锁定 60 FPS，最差帧 17.06ms（≈58.6 FPS 的单帧），没有掉帧尖峰，`instant=false` 说明走的是真弹簧而非瞬移。

### 界面走查

逐页截图（`--preview-tab=<页>` 各自独立启动，不是点一次切一页），17 个页面在深色下逐一目视，
并抽查浅色（`--preview-light`）。核对项：

- 侧栏 18 行的彩色方块与选中行的模块色填充；
- 页头方块与页面模块色一致；
- 卡片顶边高光干净无接缝（4× 放大逐像素看过）；
- 深色/浅色两种外观下卡片都能读出"被照亮"（浅色下渐变方向相反，顶白无效时改由底边定义）；
- 空态、错误态、加载态均有真实文案与下一步；
- AX 树中 18 行 sidebar 的 Help 全部是"这页干什么用"的说明句。

### 尚未在本机验证的部分（明确边界）

- **真实聊天数据下的界面**：本次走查跑在 `--preview` 演示数据（界面自述"全部为虚构数据"）。
  真实微信库的读取路径未在本次改动中触碰，但真实数据下的观感未复验。
- **浅色外观只抽查了 3 页**（关注谁 / 使用指南 / 今天），未逐页复验。
- **浮窗（island）的展开态截图受抓帧时序限制**：面板靠鼠标退出自动收起，
  外部抓帧常落在掩膜动画中途。已用"多次采样取最宽帧"拿到简报卡完整帧，
  其余浮窗状态（peek / 行展开）沿用既有 QA 流程，未逐帧复验。
  浮窗内容的正确性由既有测试（IslandStyleTests / IslandRowExpandTests / CompanionMotionTests）覆盖。

## 质检测量：与 CleanMyMac 的量化对比（第二轮）

上一轮是「看起来齐了」，这一轮改成量。方法：把 CleanMyMac 5 的窗口截到本机全屏截图的像素坐标，
两边用同一套采样代码，量「最平的那块地面」的通道极差 max(R,G,B) - min(R,G,B)。
选通道极差而不是亮度，因为它正是「这个房间是什么颜色」的可测代理量。

### 第一轮结果：不达标

| | 地面通道极差 |
|---|---|
| CleanMyMac | **59.7** |
| 我们（原始 0.055） | 8.0 – 16.0 |

模块底色在数学上存在，但比参考弱 4–7 倍，弱到没人会注意到——
也就是说，**这个功能自己声称的目的（切模块会换房间）当时并没有真正达成**。
这不是审美分歧，是功能没做到。

### 修的过程（两次被自己的测试拦下）

先只调大透明度，被 `testStrongestModuleTintKeepsOnWashTextAtAA` 拦下：
今天页地面给 55% 白副标题只到 **4.389:1**，低于 AA 的 4.5。

于是去量参考产品为什么敢用 58：它的地面相对亮度是 **0.058**，
在它上面 55% 白文字只有 **2.9:1**——**参考产品自己是不合规的**。
它敢这么做，是因为它的地面上**只放又亮又少的字**，不承载密排小字。

所以这不是「把透明度调小一点」的问题，是结构问题。
抄它的结构而不是数字：**把落在底色上的字提亮**，用提亮换回地面的颜色额度。

- 页头副标题与日期改用 `onWashSecondary()`（深色 80% 白，浅色走常规 secondary）
- 地面亮度上限不再拍脑袋，而是从「落在它上面的字必须过 AA」反解出来
  （`ambientLuminanceCeiling`，解 (L_text + 0.05) / (L_ground + 0.05) = 4.5）
- 底色强度由两个约束夹住并取最小值：**按通道极差归一化**
  （不同模块色极差不同，玉色 97/255、琥珀 179/255，同一个透明度会让琥珀房间比玉色房间强一倍多）
  与**亮度天花板**。

### 最终结果

| | 地面通道极差 |
|---|---|
| CleanMyMac | 59.7 |
| 我们（原始） | 8.0 – 16.0 |
| 我们（现在） | **23.5 – 35.3** |

余下差距是**结构性的、有意保留的**：参考产品的窗口是一张海报，
我们是一个承载 20 行消息的工作台。它的 60 是整页饱和色场，密排文字的界面用不了。
我们停在「一眼能看出换了房间」的强度。

### 可读性实测（渲染像素，不是推算）

| 区域 | 地面 | 文字 | 实测对比度 |
|---|---|---|---|
| 页头（色晕最强的位置） | 34–52 | 222–226 | **10.0 – 10.7:1** |
| 卡片正文 | 30–34 | 221–255 | **11.7 – 16.5:1** |

AA 门槛 4.5:1。页头文字有 2 倍以上余量，不是擦边过。

### 这一轮修掉的真实缺陷

| 缺陷 | 事实 |
|---|---|
| **浅色外观下页头整块消失** | 新加的 onWashSecondary 把颜色写死成白色，浅色画布上变成白底白字。改为按外观分支。这个 bug 只有浅色截图会暴露。 |
| 模块底色强度不归一 | 同一个透明度下，琥珀房间比玉色房间强一倍多（30.9 vs 13.8）。改为按各色通道极差归一化。 |

### 新增的质量门（都验证过能失败）

`CompanionMaterialTests` 从 15 个增加到 18 个，新增三条：

- `testStrongestModuleTintKeepsOnWashTextAtAA`：18 个模块 × 最强强度，
  落在底色上的字必须 ≥ 4.5:1。**第一次跑就拦下了 4.389**。
- `testWashIsPerceptiblyStrongerThanTheOriginalTint`：每个模块渲染后的通道极差 ≥ 8/255，
  防止把「满足可读性」做成「把功能删掉」。
- `testModuleWashesAreNormalisedToComparableStrength`：最强与最弱模块的差距 ≤ 3 倍。

### 结论：能不能算「堪比 CleanMyMac」

分项回答，不含糊：

| 维度 | 参考 | 我们 | 判定 |
|---|---|---|---|
| 底面颜色场强度 | 59.7 | 23.5–35.3 | **接近，未追平**（结构性差距，见上） |
| 模块色贯穿（侧栏块 / 页头 / 底色 / 选中行 / 主按钮） | 有 | 有，18 个模块 | 达到 |
| 表面光照（顶边高光 + 渐变 + 单层柔影） | 有 | 有，深浅两套 | 达到 |
| 主操作发光 | 有 | 有（`CompanionGlowButtonStyle`） | 达到 |
| 动效 | 平滑 | 形态弹簧 60.0 FPS，最差帧 17.06ms | 达到 |
| 文字对比度 | 部分不达 AA（2.9:1） | 10.0–16.5:1 | **超过参考** |
| 信息密度 | 一页三要点 | 一页可承载 20 行消息 | 不同品类，不做比较 |

**诚实结论：质感已经是同一水平线，但不是同一个东西。**

- 参考产品的「高级感」有相当一部分来自**大尺寸主视觉**（那颗 3D 圆盘占了窗口 1/3）
  和**整页饱和色场**。那两样在密排文字的工作台上不可用——不是我们做不到，是用了会更差。
- 我们真正的差距在**底色强度**这一项，且是刻意停在 23–35 而不是 60。
  理由已量化：60 会让页头副标题掉到 AA 以下。
- 我们有一项**超过**参考：文字对比度。参考产品在色场上放 55% 白文字只有 2.9:1，
  属于不合规；我们是 10.0–16.5:1。

因此：**「堪比」成立，「等同」不成立，且不应该追求等同。**
若要继续压缩差距，可动的只剩一个方向：**把底色的强区从「页头一整条」收成「页头与内容列错开的斜向渐变」**，
让内容列落在弱区、标题区落在强区，从而允许强区更饱和。这属于下一轮的设计工作，本轮未做。

## 第三轮：按社区源码质检 HUD 浮岛（2026-09-15）

上一轮量的是工作区。这一轮按要求去 GitHub 找高星 macOS 浮岛实现读源码，
重点核浮岛本身的交互、布局、动画帧率与展开状态样式。

### 读了什么（真实源码，非描述）

| 仓库 | 读到的内容 |
|---|---|
| `TheBoredTeam/boring.notch`（约 10.6k★） | `ContentView.swift` 全文、`NotchShape.swift`、`NotchHomeView.swift` |
| 其来源 `MrKai77/DynamicNotchKit` | 经前者的文件头注明 |

### 对照后确认的三处差距（均已修）

**1. 外形只能缩放，不能变形 —— 最实质的一处**

参考实现的 `NotchShape` 把 `topCornerRadius` / `bottomCornerRadius` 声明为可变，
并实现 `animatableData`（`AnimatablePair`），让圆角在过渡中插值：
**形状本身在重塑，不只是窗口变大**。

我们三个半径（22 / 10 / 16）在**每个调用点都是字面量、每个状态都一样**，
所以浮岛只能被拉伸——32pt 药丸的曲率一直锁着，哪怕岛体已经长到 250pt。
这正是"一个窗口变高了"和"浮岛展开了"的区别，而且**只截两端状态是看不出来的**。

改为状态驱动：闭合 22 / 10 / 16，展开 16 / 12 / 20（展开后更方，因为它是面板不是药丸）。
硬件缺口几何**不参与插值**——那会让缺口在每次过渡中滑离真实刘海。

**2. 圆角会瞬跳**

外层有 `.animation(nil, value: presentedState)`（为避免内容与遮罩弹簧交叉淡入），
它同样会抑制这里的隐式动画——**光加 `animatableData` 不够，圆角仍会瞬跳**，
而岛体在弹。新增 `islandSilhouette(expanding:)` 并把动画**作用域收到形状本身**。

弹簧参数特意对齐窗口帧弹簧（展开 0.42/0.82、收起 0.26/**1.0**），
**不是**内容 morph 的 0.30/0.88——形状必须跟着帧走，否则圆角会领先或落后边缘。

**3. 没有场景合成**

参考实现用 `.compositingGroup()` 把 notch 场景合成一次。
我们一个都没有：每个半透明层（AI 扫光、光晕、行 hover）和带阴影的层各自对窗口混合，
结果是过渡中带阴影的轮廓与不透明缺口带相接处有接缝，且每层每帧多一次离屏。已加。

### 顺带修掉的**活 bug**

内容 chrome 的 `UnevenRoundedRectangle` 把圆角写死 `bottomLeading/bottomTrailing: 22`，
**没跟着轮廓走**。半径改为状态驱动后，它就成了唯一还钉在 22 的地方：
描边和它投的阴影会落在与所属形状不同的圆角上，过渡的一端能看到边框切进圆角里。
已改为读同一份来源，并加源码扫描门（防止任何调用点再写字面量）。

### 交互与帧率实测（每一处点击、移入移出）

原有验收只能测 `--preview-peek` 走过的一条路径，等于"两条转换 60 FPS"，
而浮岛有七条，且每一条都由用户自己的点击或光标移动触发——任何一条卡顿都会被看见。
新增 `--preview-transitions`，走真实入口（`mouseEntered` / `mouseExited` / `goExtended` /
`collapse`），每条腿等弹簧落定后读面板本来就每 vsync 记录的 `IslandFrameTiming`：

| 转换 | 起点 → 终点 | FPS | p95 帧 | 最差帧 |
|---|---|---|---|---|
| 移入（compact → peek） | compact → peek | 60.4 | 16.67 ms | 16.68 ms |
| 停留展开 | peek → extended | 60.0 | 16.69 ms | 16.69 ms |

### 第四轮：抓到一个「浅色外观下功能静默失效」的真 bug（2026-09-15）

这一轮由我自己的测试套件异常崩掉引出：`swift test` 返回 EXIT=1，
原因是 `CompanionMaterialTests` 里我写的 `strengths.min()!` 在空数组上解包 nil，
**直接带崩了整个 xctest 进程**。修掉强制解包后，测试立刻报出失败，
暴露了一个更深的问题：

**浅色外观下模块底色完全不存在（alpha = 0）。**

原因：亮度模型只会把地面**提亮**，并以此为前提守卫：

`guard relativeLuminance(tint) > relativeLuminance(canvas) else { return 0 }`

近白画布上没有任何强调色比它更亮，这个守卫对**所有模块**都成立，
函数一律返回 0 —— 也就是说这个功能在一半外观下从来没生效过。
前一版能过，只是因为测试只测了深色，而且我还用强制解包把它崩掉了。

**修法**：模型改为显式接收外观（不再依赖环境），两种外观方向相反：

- 深色：提亮地面，受**亮度天花板**约束（文字是提亮后的 80% 白）
- 浅色：压暗地面，受**亮度地板**约束（文字是常规 secondary，约 0.42 sRGB）

浅色另加 `lightAppearanceTintScale = 0.38`：同一个色叠在近白地面上比叠在近黑上
看起来强得多，所以要按**感知**归一，而不是按**测量值**归一——否则两种外观会
被测到一样强，看起来却差一倍。

同时把画布颜色做成显式常量（`canvasRGBDark` / `canvasRGBLight`），
两种外观都能被确定性断言，不依赖跑测试的机器是什么外观。

**测试也改了结构**：原来按模块循环，抓不到「所有模块一起归零」；
现在按**外观**外层循环、模块内层，这正是能抓住该 bug 的形状。

实测（浅色外观，渲染像素）：

| 页面 | 地面通道极差 | 修复前 |
|---|---|---|
| 怎么用 | 2.3 | 0 |
| 提醒方式 | 1.7 | 0 |

数值比深色小是**设计如此**（近白地面上同色更显眼），但不再是 0。

### 这一轮新增的门（21 条，都能失败）

- `testEveryModuleRendersAWashInBothAppearances`：18 模块 × 2 外观的 alpha 必须 > 0。
- `testEveryModuleWashIsPerceptiblyStrong`：两种外观下通道极差都要 ≥ 5/255。
- `testModuleWashesAreNormalisedWithinEachAppearance`：最强/最弱 ≤ 4 倍。
- `testLightAppearanceWashKeepsItsGroundAboveTheFloor`：浅色下不许把地面压到读数地板以下。
- `testLightWashIsWeakerThanTheDarkOne`：浅色必须**弱于**深色，防止以后「对齐两个数值」把它改错。
- 全部去掉强制解包：测试崩掉进程等于**没有任何测试结果**，比红更糟。

### 最终验证

- `swift test`：**1570 通过，0 失败**，11 个显式跳过，无 crash。
- `swift build -c release`：零警告零错误。

### 测量过程中修掉的三个测量 bug（都是"看起来有结果、其实没有"）

这一轮的坑全在测量本身，值得记下来，因为每一个都会静默产出错误结论：

1. **报告了错误的终点状态**。收起腿读成「extended → extended」，因为
   `collapse()` 在下一个 runloop turn 才生效，而终点是调用后立刻读的。改为落定后读。
2. **固定等待猜测落点**。改为**轮询目标状态**并记录抵达耗时；
   固定 sleep 要么等过头，要么把**上一个状态**记成终点——
   正是 hover-out 腿第一次报「peek → peek，0 帧」却看起来像通过的原因。
3. **读到被清空的样本**。`IslandFrameTiming.begin()` 会清零当前采样，
   所以只要中途发生一次重定向（内容重新测量、下一条腿开始），
   之前的数据就没了，读出来是「0 fps」——
   **一个看起来像结果、实际上是"没有结果"的数字**。
   改为 `finish()` 把每次完成的运行存入历史，测量读历史而不是读易失的当前值。

### 一条腿无法在活体测量，已如实标注

`peek → compact`（光标移出未停留的药丸）在活体测量里始终测不到帧，

`isMouseInside` 翻回 true，于是折叠被正确地取消。

该路径的正确性由**单元测试**覆盖并通过：
`IslandPeekTests.testLeavingPeekBeforeDwellDoesNotOpenInbox`
（peek → mouseExited → 0.35s 后为 compact）。

因此这一条是**有状态覆盖、无活体帧率覆盖**，属于测量边界，不是质量失败。
若将来要活体测它，需要一个"抑制真实指针监视器"的预览专用开关——
本轮没有为测量而增加产品表面。

### 另一个环境坑：锁屏会静音 display link

看护用的 Watch Dog 已按此配置：只在**实质变化**时通知。

## 第五轮：对照 wechat-intelligence-hub 的底层读取机制（2026-09-15）

参考仓库：`Rion-Wu-tech/wechat-intelligence-hub`（`v0.9.2-preview.2`）。

**许可证是 AGPL-3.0。** 与本项目之前的做法一致：只借鉴机制与接口约定，
**不复制任何代码、文案或素材**。本文记录的是对公开数据契约与状态机的理解，
不是代码移植。

### 读了什么

| 文件 | 读到的内容 |
|---|---|
| `projects/rion-wechat-reader/README.md` | Reader 的能力边界与降级路径 |
| `projects/rion-wechat-reader/docs/access-bundle-compatibility.md` | 两种密钥材料格式的**精确**数据契约 |
| `skills/wechat-cli/references/access-onboarding.md` | 五步首次接入流程与完整状态表 |

### 对照结果：三处我们确实缺的

#### 1. 密钥格式只认一种，其余**静默丢弃**（最严重）

我们原先只接受：

```json
{ "message/message_0.db": { "enc_key": "<64 hex>" } }
```

`loadKeys` 对其他形状一律 `continue`，**一条都不报**。于是任何别的格式都会
加载出 0 条密钥，然后 Reader 报「这个库没有对应密钥」——
用户读到的是**「我的密钥不对」**，而真相是**「这个文件不是我能读的形状」**。
这是最贵的一种错：人会去找新密钥，而他手上的那把从来没问题。

现接受三种形状（按生态产出的顺序）：

| 形状 | 形态 | 来源约定 |
|---|---|---|
| 1. 路径表·对象式 | `{ "<rel path>": { "enc_key": "…", "salt": "…" } }` | 本项目自己的密钥准备所写 |
| 2. 路径表·裸字符串 | `{ "<file name>": "<64 hex>" }`，并接受 `key` 作为 `enc_key` 别名 | 公开生态的另一种约定 |
| 3. schema-2 salt 表 | `{ "schema_version": 2, "keys": { "<32 hex salt>": "<64 hex key>" } }` | 以每个库**自己的前 16 字节**为键 |

并且：无法识别的条目**被计数**（`rejectedKeyEntryCount`）而不是被丢掉，
所以「文件里一条都没认出来」现在是一个**可见状态**。

#### 2. salt 寻址：内容寻址，而不是路径寻址

形状 3 真正的价值不是"多支持一种格式"，而是它**按内容寻址**：
路径表在数据库被改名或移动的那一刻失效，也无法表达"收集时就不知道路径"的密钥集。

而**我们自己写出的密钥文件里本来就有 `salt`**（`WeChatKeyPreparationService` 写的），
Reader 却从来不用它。也就是说：我们一直在写一个自己读不懂的字段。

现在路径查不到时，会读数据库前 16 字节，用 salt 再查一次。
只读 16 字节，且只在存在 salt 条目时才发生——纯路径密钥文件付出的是零次 I/O。

#### 3. 引导流程的状态太粗，且没有权限态

我们原有 6 个状态，参考有 15+ 个，且每个都带**明确的下一步**。补了两个我们真的能检测的：

- **`looseKeyPermissions`**：密钥文件对本机其他账号可读。密钥被泄露就是密钥被泄露，
  这是自己的状态而不是脚注——修法是 `chmod 600`，不需要重取密钥。
  只检查 group/other 位：owner 读不到已经由 `.unreadable` 表达，重复判定会把一个问题报成两个状态。
- **`unrecognizedKeyFormat(recognized:rejected:)`**：能打开但没有认识的格式。
  文案明确写「这不代表密钥不对，只代表文件格式不被支持」——直接对冲上面第 1 条那个误导。

判定顺序也有意为之：**密钥问题排在目录问题前面**。目录正确但密钥不可读同样读不到东西，
先把可操作的那个问题说出来，用户才不会去重选一个本来就对的目录。

### 明确判定为**已经做到**、不改的部分

对照后确认这几处我们本来就对，记下来免得以后误改：

- **zstd 压缩内容**：`WCDB_CT_message_content=4` 的 zstd 解压我们已实现（`WeChatParser`，
  静态链接 libzstd）。
- **不打开微信正在写的原文件**：我们不是复制到临时目录，而是解密成独立快照，更强。
- **WAL 处理**：我们有自己的 `WALReplay`，并且注释里已经记录了一个真实陷阱——
  微信 flush 时会让 WAL 头盐失效、真实内容落进主库，所以只 apply WAL 是不够的。
- **「可读 ≠ 已连接」**：我们的 `.ready` 文案本来就写着「账号与密钥是否匹配，仍需以成功同步为准」，
  正是参考文档强调的 `ok:true` 只表示检查完成。
- **缺密钥时的有界尝试**：参考强调不要循环重试；我们的接入流程没有自动重试循环。

### 验证

- `swift test`：**1589 通过，0 失败**（新增 19 条），11 个显式跳过，无 crash。
- `swift build -c release`：零警告零错误。
- 新增的 19 条门**验证过能失败**：把裸字符串解析改回旧行为、并禁用 salt 查询后，
  **13 条立刻失败**——其中 `testReaderLoadsBareStringPathMap` 报出 `recognized=0, rejected=1`，

  它写文件时用默认 umask（0644），而 0644 确实是过宽权限。
  已把该测试的权限固定为 0600，让它只测它真正要测的那条轴（可用性 ≠ 可解析），
  权限轴由新测试单独覆盖。

## 第六轮：对第五轮改动的对抗性质检（2026-09-15）

质检目标：我给上一轮打分之前，先假设它有问题。

### 抓到 1 个我自己造的静默缺陷（与上一轮批评对方的是同一类）

**`keyFilePermissionsAreLoose` 被声明、被读取，但从未被赋值。**

```swift
private(set) var keyFilePermissionsAreLoose = false   // 永远是 false
```

后果：`looseKeyPermissions` 这个诊断状态**在真实应用里永远不可能触发**。
一个存在、两半都有测试、却**不可达**的状态。

更值得记的是**为什么测试没抓到**：我分别测了两端——
`accessMaterialState` 会返回 `.loosePermissions`、判定策略能从手写事实里产出该状态——
但**没有任何测试**把两端接起来。两端都对，中间那根线是断的，而两端各自的测试都绿。

这正是我上一轮批评对方密钥加载器的那类缺陷：**看起来有覆盖，实际没有**。

**修法不是补一句赋值**：改成计算属性。
一是只能有一个实现；二是权限会在进程运行中变化——用户 `chmod 600` 修好之后，
存下来的值会一直报旧模式，直到密钥文件碰巧被重新加载。

**补的测试是端到端接线**（`WeChatKeyMaterialTests`，3 条）：真实 reader + 真实密钥文件 + 真实判定，
不手写任何事实。并**验证过能失败**：把字段改回恒 `false`，测试报
`ready(...)` 而非 `looseKeyPermissions` —— 即「世界可读的密钥文件被告诉一切正常」。

### 顺手收掉的重复

两个调用点各自抄了同样 5 行构造事实。这和我在浮岛圆角上修过的是同一类问题，
新增 `KeyMaterialFacts(reader:)` 收成一处——它同时让**整条链路可测**，
这正是逐字段构造函数做不到的。

### 第二处：诊断被藏在默认折叠的「高级连接设置」里

`databaseSection`（含权限警告）在 `DisclosureGroup` 内，而 `showAdvancedConnection` **默认 false**。

这不是美观问题，是**有效性**问题，而且两个密钥问题的行为不同：

| 问题 | 读取行为 | 主面板是否已能看见 |
|---|---|---|
| 格式不认识 | **读取失败** | 能——「读取聊天 待连接」 |
| 权限过宽 | **读取完全正常** | **不能**——什么都不显示 |

所以权限问题会**无声无息地一直存在**，藏在一个折叠区后面。

**修法**：在主面板加一条**条件渲染**的警告，只在真有问题时出现（默认界面保持原样）。

### 第三处：`dbDir` 为空时的路径拼接

`keyByHeaderSalt` 用 `"\\(dbDir)/\\(normalized)"` 拼路径，而 `dbDir` 是普通字符串，
账号探测失败时为 `""`——会拼出 `/message/message_0.db` 这种**根目录下**的绝对路径。
已确认现有两个调用点都传内部相对路径、无用户可控输入，但加了空守卫。

### 视觉闭环实测（不只是编译过）

这一轮我改了视图代码，所以**必须实测渲染**，不能只看编译通过。
预览默认用不存在的 `no-keys.json`，看不到警告，于是造了真实场景：

### 复核后判定为**不是**问题的

- **`findKey` 是否成为文件读取原语**：查了全部生产调用点（2 处），
  都传内部相对路径，没有用户可控输入。
- **重复删除是否误伤**：那个重复行常量带 `-wal` 后缀，与被删的 `-wal` 行不同，未受影响。

  不过它藏在折叠区里——所以主面板那条警告是必需的，不是重复。
