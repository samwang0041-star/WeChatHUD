# WeChatHUD 产品化改造与验收

## 产品判断

WeChatHUD 的价值是把聊天转成可解释、可处理、可回溯的工作线索。常驻灵动岛负责低打扰提示，原生工作台负责集中处理，聊天详情负责理解与回复。不能用更多 AI 按钮替代可靠的读取、正确的责任归属和实际保存结果。

既有功能覆盖已经较广，但原实现存在突发消息跳过、AI 失败后漏分析、群聊对象混淆、完成判定过宽、设置覆盖用户配置、处理状态保存失败仍消失、历史查询先截断后筛选等问题。因此本轮同时调整交互和底层处理。

## 功能盘点与本轮结果

| 用户任务 | 既有能力 | 本轮落地 |
|---|---|---|
| 平时安静，有事提醒 | 吸顶浮窗、像素伙伴、通知 | 保留左右翼与伙伴；通知避让刘海，延时不被动画误取消；不打断已展开的详情；支持减少动态效果 |
| 知道对方找我做什么 | 摘要、分类、回复债务 | 首页直接显示重要事项；详情先显示本次来意、原消息和上下文入口；分类考虑群聊实际被提及对象 |
| 理解为什么 @ 我 | 群上下文简报 | 保留真实 @ 消息锚点，后续普通消息不覆盖；不确定对象进入复核；无法读取时明确显示原因 |
| 回复而不丢草稿 | AI 建议、输入框、自动托管 | 对话草稿按收件人隔离；新增可编辑草稿工作台；保存失败保留文本；托管保持默认关闭 |
| 分清我要做和等对方 | 双向事项、我的承诺 | 首页数量直达对应筛选；完成、撤销、处理记录、恢复互通；原文定位按时间和消息锚点查询 |
| 避免错误自动结案 | 承诺完成推断 | 要求主题匹配和明确完成信号，拒绝无关附件、否定、计划、问句和部分完成 |
| 回看一段聊天 | 洞察、日报、历史复盘 | 时间范围前推到 SQL，排除未来摘要，披露截断和媒体能力限制 |
| 配置并知道是否在工作 | 分散设置和引导 | 原生侧栏、分步引导、当前连接与下次配置分开；显式选择账号；最近成功同步、可读密钥状态、真实连接测试 |
| 在不同微信账号间使用 | 原先共享业务库与缓存 | 缓存和业务库按账号目录隔离；旧库保留，未知归属不自动认领；新账号库无业务资料时可显式确认绑定，重启生效 |
| 突发消息不漏分析 | 扫描与讨论提取 | 分类、讨论和承诺来源使用持久队列；最旧失败阻塞新批；失败指数退避；首页显示待整理数量并可重试 |
| 质量随使用提升 | AI 输出没有纠错闭环 | 待办支持责任纠正；完成、忽略和责任纠正写入反馈；同类对话的下一次提取读取最近纠正提示 |
| 人工回复不被误判成功 | 只按发送按键判断 | 人工发送后核对账号本地快照中的新出站消息；不能确认时保留草稿并给出下一步 |

## 已完成的原生交互验收

![原生工作台，虚构演示资料](assets/productization-2026-09-07/workspace.png)

![消息通知](assets/productization-2026-09-07/notification.png)

使用单独 `WeChatHUD Preview.app` 与虚构资料操作，不读写真实微信，不触发实际发送。

- 首页“等对方”进入正确责任筛选；完成后进入处理记录；恢复后首页计数回到 1。
- 原文缺失显示“不可用”，不伪造来源；Escape 正常关闭来源弹层。
- 回复存为草稿、在草稿页继续编辑并显示自动保存结果。
- 四步首次介绍可完成，未配置项明确显示，不将“点击完成”当成连接成功。
- Cmd+1 打开工作台，Cmd+, 进入设置，标准应用菜单可用。
- 模拟消息展开为完整通知，正文及上下文、查看对话、微信入口、收件箱按钮可读；通知不再被动画结束的伪鼠标退出提前收起。
- 详情正文位于顶部刘海之下；连接和 AI 设置使用原生控件，测试需显式触发。
- 待办工作台已验证“责任错了”菜单：把“我要做”改为“等对方”后，界面标签即时更新，事项状态不变，并写入质量反馈。
- 旧版资料维护已有安全入口；测试确认未绑定前不自动接回，显式确认当前账号目录并重启后才恢复旧数据。
- **真实微信数据与实时 AI 链路实测验收通过**：成功接入本机真实微信数据库（包含 12,313 个联系人，2,720 个会话），实时增量 FSEvent 扫描与会话捕获正常；配置 DeepSeek 线上模型验证通过后，实机测试真实群聊“中心组长群”的 @我 消息：AI 自动生成了一句话摘要“汇报材料已定稿，明天下午开会通知”，成功提取出话题、决议和发言人依据，生成上下文回复建议，并验证了一键存入回复草稿箱。
- 队列测试覆盖 100 条乱序突发、45 条分窗、100 条分批、覆盖扫描、重启恢复、旧失败阻塞新行和整体事务回滚。

## 发布边界

本机源库只读自检：发现 1 个候选账号，可读取 2,720 个会话；检查最近 2 个会话后成功读取 1 条消息，仅输出数量，不输出消息正文或密钥。打包提示词可加载。旧资料状态为“待确认账号归属”，因此新的隔离账号库关注数为 0；旧版进程保持运行，没有用新版替换它。

这是可构建、可签名运行的原生客户端改造，包版本提升到 1.1.0。633 个自动化测试通过（1 个 live-AI 用例按设计跳过）；release 构建和正式、演示两个 app 包均通过签名校验。在真实微信运行态下完成了端到端闭环验证。

- 没有发送真实微信消息；发送前的账号核验失败时必须保留草稿并阻断操作。
- 历史洞察有消息数量上限，不能宣称已阅读全量聊天。媒体内容也不能因出现附件就推断其语义。
- 未知归属旧库保留在原路径，需核实账号后恢复；不能自动拿当前唯一账号认领历史资料。
- 仍需真实使用样本的误报/漏报评估、长期资源占用与微信版本兼容观测；本轮不以模拟测试代替这些证据。
- 尚未进行公证、自动更新、商业分发或远程部署。面向他人使用前，需要完成签名分发、版本兼容支持和明确的数据处理说明。

## 后续能力优先级

1. 建立可纠正的质量反馈：区分“并非找我”“责任人错了”“重复事项”，让修正有回执并能用于离线评估。
2. 将重要事项形成持续跟进：到期、延期、对方交付、重新打开共享同一事项记录，避免每次分析产生新的孤立待办。
3. 给历史洞察增加覆盖率和继续分析入口，使较长区间可分段完成并能定位每条结论的依据。
4. 完成多版本微信长期兼容和分发升级测试，再扩大用户范围。

## 本地复现

```sh
swift test
make app
make preview
open ".build/WeChatHUD Preview.app"
```

`make preview` 使用独立应用标识和虚构资料，不启动微信扫描。`make self-check` 对微信源库只读，可能初始化助手自己的设置与隔离业务库；输出会话数量和能力状态，不输出聊天正文或密钥。正式应用打包已将提示词资源放入 `Contents/Resources`，避免依赖源码目录才能启动。
