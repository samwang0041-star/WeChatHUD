# 待办 / 我答应的事：严格度等级设计方案（2026-09-12）

用户诉求：质检「我答应的事」和「待办」的抽取算法是否过于宽松，并设计一个滑动等级控制严格程度。

本方案由四路并行评审收敛而成（算法漏斗、产品设计、架构实现、红队反驳），
原始报告见 `/tmp/hud-design/{A-algorithm,P-product,E-architecture,R-redteam}.md`。

## 一、结论先说：不是「聊天进多了」，是「队列语义混了」

本机真实数据（只读聚合，未读正文）：

| 事实 | 数字 |
| --- | --- |
| 待办总计 / 待处理 | 3067 / **792** |
| 其中纯记录类（info+timePlace） | **449 条（56.7%）**，info 占 pending 52% |
| 我方真正要做（todo/question，owner=mine） | 106 条（13.4%） |
| 默认视图「我要做」 | **115 条 / 29 个会话** |
| 产出条目的会话 | 92 个（白名单 115）—— 逐条筛，非整会话涌入 |
| 用户实际处置 | archived 2274 条（74%），`done` 仅 **1 条** |

两点被数据推翻的假设：

1. **“很多聊天都进来了”不成立**。默认视图 29 个会话、平均每会话 4 条；
   54 个会话有 pending，其中 38 个已清空。问题在**类型**不在**会话数**。
2. **“抽取器很宽松”已过时**。`discussion_v3` 是活的（源消息滞后 0 分钟）；
   产出量 v2 峰值 1289 条/天 → v3 约 41 条/天（5–13 个会话）；591 次调用中
   39.8% 产出 0 条。**pending 里 90% 是 v2 遗留**（v2 716 / v3 76）。

## 二、为什么不能用置信度做滑杆

置信度分布饱和：≥0.8 占 94%（0.9 档 2004 条、0.8 档 781 条）。
滑杆在真实数据上是**开关而非渐变**：

| 切点 | 剩余 | info 占比 | 我方待办保住 | 误杀 |
| --- | --- | --- | --- | --- |
| 不切 | 792 | 52% | 106 | 0 |
| ≥0.90 | 533 | 55% | 86 | 28 |
| ≥0.93 | 127 | 59% | 23 | **91（76%）** |

越调严越只剩**信息**、越删掉**正事**——因为事实类文本（“预算 30 万”）天然高置信，
而 todo/question 才是低置信区。**滑杆主变量必须是 kind × owner，不是 confidence。**

对照组：`commitments`（我答应的事）在 ChatMonitor 侧有 **0.72 硬门槛**且全部 ≥0.7，
而 `discussion_items` 抽取侧**零门槛**——这是两个页面观感差异的根源。

## 三、推荐方案：三档严格度，锚在结构性判据上

| 档位 | 放行什么 | 本机可见量 | 用户看到的后果 |
| --- | --- | --- | --- |
| 全记 | 全部 pending | 792 条 / 54 会话 | 状态条写明「信息备忘 413 条在下方，不计入待办」 |
| **只留要做的（默认）** | `kind != info` | 373 条 / 52 会话 | 列表内 info 为 0；状态条「已收起 413 条」 |
| 只留压在我身上的 | `(kind ∈ {todo,decision} && owner ∈ {mine,theirs})` 或 7 天内到期 | 163 条 / 36 会话 | 状态条「已收起 629 条」 |

不加第 4 档：下一档自然是“必须有截止时间”，本机只剩 **35 条**（真实 due_at 仅 5.1%），
等于清空列表。

**默认档选「只留要做的」**：最严档会误杀 140 条“我指派出去的”待办（正是要跟进的），
且 96% 条目无期限，以时间为主筛选必然误伤。中档的删除线是纯 kind 维度，用户可自行复算。

## 四、实现形态：读时过滤（方案 A）

抽取与入库照旧全量保存，等级只作用于**读取层**：拨档即刻生效、可来回拨、零 AI 成本、零等待。

对比否决方案：

- **写时闸门**：调松后**无法恢复**——游标已消费、队列已删除，全仓无游标回卷 API。
- **落库打标**：需改表 + 双路读写，且新旧行口径不同，回填不可逆。

硬边界：**手动 done / dismissed 的条目永不被档位复活**；VIP 会话条目豁免收起并在行上标注；
「我答应的事」不设档位（它天然已是最严一类、已有 0.72 门槛），只显示一行说明。

必须进缓存键与日报指纹：`DiscussionItemsCache` 与日报指纹（否则拨档后视图/日报不刷新）；
等级**不进** `prompt_version`（那列描述“行是怎么产生的”）。

## 五、顺带发现的真实缺陷（与本设计直接相关）

**P1 `due_at` 空值写成空字符串而非 NULL**（HUDStore 写入端 `?? ""`，列声明 INTEGER）：

```text
typeof(due_at): text 2911 行 / integer 仅 156 行
due_at IS NULL   → 0 行（恒假）
due_at > 0       → 3067 行（恒真！空字符串在 SQLite 中大于任何数字）
```

后果：任何“按截止时间筛选/判断有期限”的逻辑会**静默把所有条目当成有期限**。
目前被 `source_timestamp` 分支掩盖（0 行超窗），属**潜伏回归**；而严格度等级若要
用 “7 天内到期” 做判据，会直接踩中它。**必须先修。**

次要：`commitment_kind` 143/182 为空；去重提示只喂最近 20 条；confidence 无限定钳制。

## 六、验收标准

- 拨档后列表条数与状态条「已收起 N 条」一致，且 N 可由用户自行复算。
- 松→严→松 往返后条目集合与初始完全一致（可逆性）。
- 拨档不产生任何 AI 调用、不写 `discussion_items`。
- 侧栏徽标、工作台、日报三个消费者在同一档位下计数一致。
- 手动 done/dismissed 的条目在任意档位都不出现。
